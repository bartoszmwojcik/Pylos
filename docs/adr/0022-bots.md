# 0022. How the bots work

## Status

Accepted for the bot list and the knobs (D15, the owner's choice on 2026-11-23). The algorithms below are implementation details chosen by the agent. The owner reviews them in the PR.

## Context

D15 asks for random, greedy, alpha-beta and MCTS bots, with one knob each, that any two configurations can play against each other. A game must be reproducible from its seed, so a surprising game can be replayed and studied.

## Decision

- Every bot is a pure function `chooseMove :: BotSpec -> Gen -> BPosition -> Maybe (BMove, Gen)` (`bots/Pylos/Bot.hs`). It uses the engine's own random generator (0018), so the same seed always gives the same game.
- Every bot runs on the bitboard engine (0020) for speed. The reference engine stays the oracle that the tests use to check each bot's moves.
- **Evaluation** (`Pylos.Bot.Eval`), shared by greedy and alpha-beta: `reserve × (my reserve − theirs) + free × (my free balls − theirs)`. Balls in reserve are what you lose by (R05). Free balls can be raised or taken back (R03, R07). The default weights are reserve 10 and free 1.
- **greedy** (knob: the two weights) plays the move whose resulting position evaluates best, breaking ties at random.
- **alphabeta** (knob: depth 1–8) uses negamax with alpha-beta pruning and the default weights. Moves with take-backs are searched first, so pruning cuts more. Root moves are shuffled by the seed, so equal moves vary between games. A loss found deeper is preferred to an earlier one, and a win found sooner to a later one.
- **mcts** (knob: iterations) uses UCT with the exploration constant fixed at √2. Each iteration walks the tree, adds one node, plays a random game of at most 200 plies (a capped game counts as half a win), and updates the path. It plays the most-visited move. It does not use the evaluation function.
- **random** plays a uniform random legal move.

Rejected: more knobs per bot (the owner chose "fewer knobs"). Rejected: an `IO` bot interface with a time limit. A pure function is easier to test and to reproduce. Depth and iteration counts give the same control.

## Consequences

- Depth is capped at 8. Bots are pure functions with no time limit, and the live server cannot cancel a running game, so the cap is a safety bound. Cost grows roughly ×6 per extra ply. Measured on this server, `pylos-match alphabeta:depth=N greedy 2` (one game as White, one as Black):

  | depth | White game | Black game |
  |---|---|---|
  | 3 | about 0.1 s | about 0.1 s |
  | 4 | about 0.2 s | about 0.2 s |
  | 6 | about 6 s | about 6 s |
  | 7 | 6.0 s | 6.2 s |
  | 8 | 39 s | 83 s |
  | 9 | 280 s | over 25 min (the 2-game run hit the 30 min limit and was killed) |

  Depth 9 exceeds the issue's ~20 min per game threshold, so the cap stops at 8 (issue #29, open question). Times vary a lot with the game, since pruning depends on the position. Depths 3, 4 and 6 are earlier measurements, not re-timed. MCTS costs about 1 ms per 10 iterations early in a game.
- In first matches, greedy beat random 4–0, alpha-beta depth 2 beat greedy 4–0, and `mcts:iterations=2000` beat alpha-beta depth 4 2–0. These are small samples, not a rating. How bots are judged is still open (D15).
