### E02-S01: The owner can build any board position and see it printed
- Backlog source: .ai/specs/product-brief.md · Backlog id: E02-S01 · Epic: E02 · Depends on: E01-S01
- Decisions in play:
  - R01: 4 levels, 30 positions, a square on levels b–d needs all 4 supports, 15 balls per side (proposal; the geometry is standard).
  - D04: pure, readable reference (active).
- Acceptance criteria:
  1. Given the board model, when all positions are listed, then there are exactly 30: 16 + 9 + 4 + 1.
  2. Given any position on levels b–d, when its supports are queried, then exactly the 4 squares beneath it are returned. A QuickCheck property checks this against the geometry formula.
  3. *Negative:* given an empty board, when a ball is placed on `b11`, then the placement is rejected because the square is unsupported.

### E02-S02: The owner can list and apply every legal move under the agreed rules (blocked by Q01)
- Backlog source: .ai/specs/product-brief.md · Backlog id: E02-S02 · Epic: E02 · Depends on: E02-S01
- Decisions in play:
  - R02: completing a square forces a take-back of 1–2 balls.
  - R03: raise rules.
  - R04: what counts as a free ball, and take-backs applied one after another.
  - R05: an empty reserve loses.
  - D08: a move is one compound value, and perft counts moves.
  - All of these are proposals pending Q01.
- Acceptance criteria:
  1. Given any position reached by random legal play, when any generated move is applied, then each colour's balls on the board plus in reserve still total 15.
  2. Given such a position, when any move is applied, then every occupied square on levels b–d has 4 occupied supports.
  3. Given such a position, when moves are generated, then the list has no duplicates under D08: the same action with the same take-back set counts once.
  4. Given a hand-built position where a placement completes an own-colour square, when moves are generated, then every move from that square carries 1 or 2 take-backs, as R02 says. If Q01 changes R02, this criterion changes with it.
  5. Given a hand-built position where removing ball x frees ball y, when moves are generated, then the take-back set {x, y} is present, as R04 says.
  6. Given the player to move has an empty reserve, when the game state is evaluated, then that player has lost, as R05 says.
  7. *Negative:* given a free ball that supports square s, when moves are generated, then no move raises that ball onto s, as R03 says.

### E02-S03: The owner can write, read and replay games in notation
- Backlog source: .ai/specs/product-brief.md · Backlog id: E02-S03 · Epic: E02 · Depends on: E02-S02
- Decisions in play:
  - D09: notation `a23`, `a11-b22`, ` x a23 a24`, and JSON game records (proposal).
- Acceptance criteria:
  1. Given any legal move from a random position, when it is rendered and parsed back, then the original move is returned.

### E02-S04: The owner can run perft and bounded playouts and freeze golden values (golden freeze blocked by Q01)
- Backlog source: .ai/specs/product-brief.md · Backlog id: E02-S04 · Epic: E02 · Depends on: E02-S02, E02-S03
- Decisions in play:
  - D08: perft counts compound moves.
  - D11: golden perft and playout files.
  - D12: bounded playout returns an outcome or `Capped`.
  - R06: the engine has no draw rule.
- Acceptance criteria:
  1. Given the start position, when `pylos-ref perft 4` runs, then it prints 16, 240, 3360 and 43680 for depths 1 to 4, with a time for each depth.
  2. Given random reachable positions, when the 8 board symmetries are applied, then the number of moves from each position is unchanged.
  3. Given any seed and ply bound, when a bounded random playout runs, then it returns either an outcome or `Capped` within the bound.
  4. Given Q01 is resolved, when the golden command runs, then a committed file holds perft values for the start position and at least 3 fixed mid-game positions, plus the outcomes of at least 100 seeded playouts.
  5. *Negative:* given a move list containing an illegal move, when `pylos-ref perft` runs, then it exits non-zero and names the first illegal move.

- Backlog source: .ai/specs/product-brief.md · Backlog id: E03-S01 · Epic: E03 · Depends on: E02-S04

### E03-S02: The owner can confirm perft and playout parity and see the speed-up
- Backlog source: .ai/specs/product-brief.md · Backlog id: E03-S02 · Epic: E03 · Depends on: E03-S01
- Decisions in play:
  - D05: perft check against the reference.
  - D11: golden perft and playout files.
- Acceptance criteria:
  1. Given the golden perft file, when the bitboard engine runs every entry, then all counts match.
  2. Given the golden playout file, when the bitboard engine replays every seed, then every outcome matches.
  3. Given the same depth, when both engines run perft with timing, then the CLI prints the nodes per second for each engine.
  4. *Negative:* given a deliberately injected move-generation bug in a test build, when a divide-style comparison is run (perft per first move), then it reports the first move where the counts diverge and the position reached.
